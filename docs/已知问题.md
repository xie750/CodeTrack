## 一、AI 底座抽取（2026-07-31）之后仍然存在的问题

这四条在做底座抽取时就已知，属于有意推迟，不是遗漏。

### 1. `allow_hint_level_3` 未被强制执行 —— 权限漏洞

**现象：** 教师在任务发布时关掉三级提示（`TaskAssignment.allow_hint_level_3 = False`），
学生仍然能拿到三级提示。

**证据：** 字段存在于 `backend/app/models/entities.py` 的 `TaskAssignment`，
`backend/app/services/seed.py` 里有两个 assignment 设为 `False`，
前端 `frontend/src/api.ts` 类型里也有 —— 但全仓库没有任何一处读它做判断。
`create_or_get_hint` 只查等级顺序，`request_hint` 只查 `student_id` 相符和课程成员身份。

**根因：** `allow_hint_level_3` 挂在 `TaskAssignment` 上，而 `Submission` 只有
`student_id` + `task_id`，**没有 `assignment_id`**。同一个 task 可以发给多个班、
各自设置不同，从 `Diagnosis` 反查 assignment 需要
student → class membership → TeachingAssignment → TaskAssignment 多跳，
且学生同时在两个班上同一门课时结果有歧义。

**当前状态：** `backend/app/ai/guardrails.py` 的 `check_hint_level_permission`
建好了函数与调用点（在 `create_or_get_hint` 内），实现为恒 `passed=True`
并带 `enforced=False` 标记。`tests/test_guardrails.py` 里有一条测试固定这个
「未强制执行」的事实，修好之后那条测试要改成断言真实的拒绝行为。

**建议修法：** 给 `Submission` 加 `assignment_id` 并回填历史数据。
注意回填本身要靠猜（同一 task 多班次时无法确定原始 assignment），
这是一个独立的数据模型决策，需要单独一轮。

### 2. 规则兜底的诊断对学生不可辨识

**现象：** 模型挂掉时，学生看到一条置信度 0.82 的诊断，界面上没有任何迹象
表明这是模板生成的、没有模型参与。

**证据：** `backend/app/services/diagnosis.py` 里兜底置信度是固定的
0.82 / 0.66 / 0.35，而 `LOW_CONFIDENCE` 阈值是 0.6。

**为什么没顺手下调：** 0.82 降到 0.6 以下会把 `status` 从 `READY` 翻成
`LOW_CONFIDENCE`，进而使 hint 请求返回 409 —— 学生在模型挂掉时连一级提示
都拿不到，同时破坏 `tests/test_demo_flow.py` 的既有断言。内置版 §17.1 的
「模型失败时降低置信度」本步**没有实现**。

**当前状态：** 数值、status、学生侧行为全部不动。降级这件事只写进 `agent_runs`
（带 `error_code`）和审计日志的 `AI_RUN_FAILED` 事件，后台可查。

**建议修法：** 前端接线时加 `is_rule_fallback` 标记透出给界面，让学生知道
这条诊断没有模型参与。这是展示层的事，不需要动置信度数值。

### 3. `SOURCE_BY_ERROR_TAG` 仍是硬编码 dict

**现象：** `backend/app/services/diagnosis.py` 的知识源选取是一个写死的
`error_tag → source_ids` 映射，只覆盖四个 error_tag。新题目没有对应条目时
拿不到任何知识源，诊断会落到 `REVIEW_REQUIRED`。

**建议修法：** 用内置版 §12 的 `knowledge_retriever.py` 替换（它不是 RAG，
只是按 course_id / student_visible / 知识点过滤的约 30 行 SQL）。
本步没做是因为接上它会改变选源逻辑，破坏 `test_demo_flow.py` 里
`kb_head_node_delete` 的断言，而当前收益为零。

### 4. 禁词列表仍以链表片段为默认值

**现象：** 默认禁词
（`ListNode* deleteAt` / `return head->next` / `head = head->next` /
`prev->next = prev->next->next`）全是链表删除题的代码，对任何第二道题目都失效。

**当前状态：** 已加 `tasks.hint_forbidden_fragments`（nullable Text，存 JSON 数组）
让禁词按题目配置，`guardrails.resolve_forbidden_fragments` 为空时回落默认列表。
**但存量题目一个都没填**，所以实际仍走默认列表。

**建议修法：** 出新题时同步填 `hint_forbidden_fragments`；存量题目按需补。

## 二、验证环境相关（与上述改动无关，但会挡住验证）

这两条在做底座抽取**之前就已经是这样**，记下来是为了下次跑验证时不误判成回归。

### 5. 13 个测试依赖 Docker，本机不可用时必然失败

`sandbox/docker_runner.py` 在 Docker 容器里跑 `g++`。本机没有可用的 docker
命令时，编译一律返回 `COMPILE_ERROR`，连带下列用例失败：

- `tests/test_sandbox_service.py::test_sandbox_service_contract_returns_structured_result`
- `tests/test_api_contract_audit.py::test_audit_logs_key_events_without_source_or_secret_details`
- `tests/test_demo_flow.py` 里 11 条依赖真实编译执行的用例

注意「本机装了 g++」不算满足条件 —— 编译是在容器内发生的。
判断是否回归时，应当与同一环境下的基线（`git stash` 后跑一遍）对比条数，
而不是要求全绿。

### 6. 发布门禁的 seed 数量断言已过期

`scripts/verify_demo_release.py` 的 `clean_migration_seed` 检查断言
`tasks == 1 and test_cases == 5`，而现在 `seed_demo.py` 会建 5 个任务、
14 个测试用例（做题业务那轮引入的）。迁移与 seed 本身都成功，只是这条计数
断言没跟着更新，所以该项恒为 FAIL。

**建议修法：** 把期望计数改成从 seed 定义里读，或直接更新成当前值。
